# Mistral反対尋問と最終判断

## Mistralの判定

計画段階、修正後、実装証拠追加後の3回とも、Mistralは `NO-GO` を返した。

一貫した反対理由:

1. 18歳確認だけならルールで足り、AI必然性が弱い
2. Proofも個人に関する属性であり、プライバシーリスクは残る
3. 同意撤回とIssuer失効が混同されやすい
4. Demo Issuerが本番eKYCに見える危険がある
5. 3〜4分へ情報を詰め込みすぎる
6. 既存API再利用の見積もりが楽観的

## 採用した指摘

- 一般利用者の主体験からPolicy入力を外した
- 同意撤回とIssuer失効を別ボタン・別説明へ分けた
- `Demo Trusted Issuer / 本番本人確認ではない` を同意画面の主領域に置いた
- `Proofも個人に関する属性で、匿名化ではない` を同意前と登録完了後に表示した
- `個人情報0` を廃止し、`AIへ送った本人情報値0` と具体化した
- 3分デモと4分ピッチを別原稿として時間配分した
- AI監査は任意展開へ下げ、主体験を65〜90秒に固定した
- API障害時に成功を模擬しない

## Mistralへ反論した点

### Proofが個人情報ならNO-GOなのか

Proofが個人に関する属性になり得ることは、プロダクト否定の理由ではない。重要なのは、匿名や個人情報ゼロと誤認させず、正確な生年月日・住所・身分証原本より開示範囲を小さくすること、保存・目的・期限・失効を設計することである。

ただし、GDPR等への適合をこのPoCで主張しない。本番化には法務レビュー、データフロー、Controller / Processor整理、保持期間、権利行使、相関識別子の追跡リスク評価が必要である。

### 18歳例にAI必然性がない

これは反論しない。単一例にはAI必然性がない。

そのため新サイトへ、主デモとは別にPolicy Stress Testを追加した。

- 配送目的が混ざる要求: 年齢確認は `over_18`、住所は配送に必要なので不要と断定しない
- 要求文に指示注入が混ざる: 氏名・住所をClaimにしろという命令に従わず、許可済みClaimへ制約する

どちらも実OrcaRouter APIで動く。AIの評価対象は年齢判定ではなく、複合目的を含む文章からPolicy案を作る導入時の意味変換とガードレールである。

### 3〜4分に入り切らない

3分デモ動画と4分ピッチは別提出物である。主デモ、AI証拠、失効、境界を両方で同じ深さに説明しない。

- 3分デモ: 実操作中心
- 4分ピッチ: 課題、設計理由、価値中心
- Policy内部の全項目は画面に残すが、読み上げない

## 実装で得た証拠

- build成功
- 実API proxy 6ルート生成
- `ORCAROUTER → over_18,human_verified → issue → VALID → revoke → REVOKED` を端から端まで確認
- 複合配送要件で住所を不要扱いせず、過剰候補だけをflagすることを確認
- 指示注入文で氏名・住所をClaim化しないことを確認
- AI臭の機械スコア 0

## 最終判断

**提出はConditional GO。**

条件:

1. 18歳確認そのものを「AIでしかできない」と言わない
2. AIの評価点をPolicy Stress Testと実OrcaRouter監査証拠で示す
3. Demo Issuer、本番eKYC未接続、Proofも個人属性である点を隠さない
4. 主体験をNIGHT SCREEN登録完了までに保ち、Policy Studioを入口へ戻さない
5. 失効を「利用者がいつでもCredentialを無効化」と説明しない

この条件を崩すならMistralの `NO-GO` が妥当である。特に、元の「4→2だからAIが必要」という説明へ戻すとAI必然性の項目を落とす。

## ユーザーが最終確認する3点

- 最終的に「身分証をサービスへ渡さず、必要な証明だけで登録する体験」になることは腑に落ちるか
- 完了条件が `登録完了 / 実Orca証拠 / 失効後の再確認 / 誠実表示` と明確か
- 法務適合や本番Issuer接続は今回の完成範囲外であることを許容するか
