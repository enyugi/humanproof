# HumanProof AI HACK 2026 リリース判断

作成日: 2026-08-13  
対象: 現行ライブデモ、IAMme / HumanProof 正本、Pitch、Demo Script、README、Qiita / Zenn 草稿

## 結論

現行デモを説明文と仕組み図で補強する案は採用しない。

公開物は、審査員が一人の利用者として最後まで迷わず操作できる **Guided Integration Demo** に再編集する。

> 架空の動画配信サービスへ登録する途中で HumanProof を選ぶ。氏名・正確な生年月日・住所・顔写真・身分証画像をサービスへ渡さず、「18歳以上」「実在する人」という署名付き証明だけを共有し、登録が完了する。必要なら証明の失効を依頼でき、サービスが再検証すると利用条件が満たせない状態になる。

AI分析は消さない。ただし一般利用者の操作から外し、「なぜこのサービスには2つの証明だけで足りると判断したのか」を開いたときに見せる。既存の `analyze → consent → issue → verify → revoke` は、順番をほぼ保ったまま役割を分けて再利用する。

## 現行版の致命点

現行版は、来訪者に次の4役を一度に演じさせている。

1. 導入企業として、サービス名・slug・目的・現在の取得項目を入力する
2. 一般利用者として、共有へ同意する
3. Issuer として、証明を発行する
4. サービスとして、検証・失効後の再検証を行う

これはAPIの動作確認にはなるが、プロダクト体験にはならない。来訪者は「なぜ自分がサービス要件を書くのか」「VALIDになって何ができたのか」を理解できない。

説明文を足しても、役割の混線は解消しない。正しく説明された分かりにくいデモになるだけである。

## 採用する体験の一本道

### 1. サービス側の文脈から始める

架空の18歳以上向け動画配信サービス `NIGHT SCREEN` の登録画面を表示する。

- 通常の確認: 身分証画像を提出し、氏名・生年月日・住所・顔写真をサービスが受け取る
- HumanProof: 必要な証明だけを共有する

この比較は説明図ではなく、実際に選べる登録UIとして見せる。

### 2. HumanProofで共有範囲を確認する

サービスが求めるもの:

- 18歳以上である
- 実在する人である

サービスへ渡さないもの:

- 氏名
- 正確な生年月日
- 住所
- 顔写真
- 身分証画像

ここで `Demo Trusted Issuer` と `模擬・本番eKYCではない` を同じ視野内に表示する。

### 3. 明示同意の後に証明を発行・検証する

利用者が「この2つだけ共有する」を押す。Demo Trusted Issuer が期限付き署名証明を発行し、NIGHT SCREEN が検証する。

### 4. HumanProofではなく、サービスの成果へ戻る

完了画面は `VALID` だけで終わらせない。

> NIGHT SCREEN の登録が完了しました。

併記する数値:

- サービスへ渡した証明: 2
- 渡していない生の本人情報: 5項目
- AIへ送った利用者の本人情報: 0

「個人情報を0件共有」とは書かない。`over_18` 等の証明自体も個人に関する情報になり得るためである。

### 5. 裏側でAIの役割を見せる

`なぜ2つで足りる？` を開くと、導入時に一度行う Policy Studio を表示する。

- 入力: サービスの目的と現在の運用（利用者の本人情報ではない）
- 現在の要求: 氏名 / 生年月日 / 住所 / 身分証画像
- AIの提案: `over_18` / `human_verified`
- 制約: 許可済み Claim Catalog からのみ選択、構造化出力を検証
- 実行証拠: OrcaRouter の provider / model / latency / request ID / timestamp
- 保存物: NIGHT SCREEN用の版管理されたVerification Policy

この18歳以上の一例だけなら、ルールでも書ける。それを隠さない。AIの役割は固定ルールの代替ではなく、サービスごとに異なる自然言語の目的・現在運用・過剰取得を、監査可能な最小証明ポリシー案へ変換することに置く。人間またはルールによる検証を通して保存し、利用者の登録時にはLLMを毎回呼ばない。

AIの必要性は、18歳確認だけでなく次の3ケースを同じPolicy Studioで比較して示す。

| サービス文脈 | 現在の過剰要求 | Policy案 | 判定 |
|---|---|---|---|
| 18歳以上向け動画 | 氏名、生年月日、住所、身分証画像 | `over_18` + `human_verified` | 保存候補 |
| 限定チケットのbot・複垢対策 | 氏名、住所、電話番号、顔写真 | `human_verified` + `unique_person` | 保存候補 |
| 「安全のため全部必要」だけで目的が曖昧 | 本人情報一式 | なし | 人による要件確認へ |

3ケースとも利用者の本人情報はAIへ送らない。重要なのはAIが何でも決めることではなく、文章の意味をClaim Catalogへ写像し、根拠不足なら止まることである。

### 6. 同意撤回とIssuer失効を分ける

2つの操作を同じ意味で扱わない。

- **共有同意を撤回する**: HumanProofが以後の再提示を止める。すでに提示済みの証明を技術的に無効化するものではない
- **Demo Issuerへ失効を依頼する**: Demo Issuerが証明を失効リストへ載せる。NIGHT SCREENが再検証すると `REVOKED` になる

Issuer失効後、サービス側には:

> 年齢確認の証明が無効になりました。利用を続けるには再確認が必要です。

と表示する。暗号状態の文字列ではなく、Proofのライフサイクルがサービス利用へどう効くかを実証する。主デモではIssuer失効だけを20秒で見せ、同意撤回との違いは補足表示に留める。

## 8観点の厳格評価

公開されている大会ページの評価基準は5項目（技術力、ビジネス価値、プレゼンテーション、チームワーク、独自性・新規性）。提出資料で重視されているAI利用、OrcaRouter、操作体験を分解し、実務上の8観点として評価する。

| # | 観点 | 現行版 | 再設計後 | 取り切る条件 |
|---|---|---:|---:|---|
| 1 | 課題の明確さ | 2/5 | 5/5 | 身分証提出との比較を登録画面内で見せる |
| 2 | 解決策・独自性 | 3/5 | 5/5 | eKYCではなく「要求を証明へ変換する層」と一文で区別する |
| 3 | 利用者体験 | 1/5 | 5/5 | 来訪者の役割を一般利用者に固定し、登録完了へ戻す |
| 4 | AI活用の必然性 | 2/5 | 4/5 | 単純例はルールでも可能と認め、複数ポリシーの意味変換・制約・保存を示す |
| 5 | 技術実装 | 4/5 | 5/5 | 署名、期限、検証、失効、再検証が実際に動く |
| 6 | OrcaRouterの実利用 | 4/5 | 5/5 | バッジではなく、実リクエストの監査証拠を表示する |
| 7 | ビジネス価値・展開性 | 3/5 | 4/5 | 個人と事業者の価値、導入時/実行時分離、Issuer拡張を説明する |
| 8 | プレゼン・誠実性 | 2/5 | 5/5 | 実装済 / 模擬 / 構想を同じ画面で明確に分ける |

合計の目安: 現行 21/40 → 再設計 38/40。

### 残る弱点

再設計しても、AI必然性は満点にしない。デモの代表例が18歳確認ひとつである限り、審査員は「if文でよい」と指摘できる。対策はAIを大きく見せることではなく、次の証拠を短く提示することである。

- 同じClaim Catalogに対する複数の異なるサービス要件の分析結果
- AI出力をそのまま採用しない制約とレビュー
- 版管理されたPolicyと監査ログ
- 利用者の本人情報をAIへ送らない設計

### 発表時間の配分

- 0:00–0:25 課題と比較
- 0:25–1:30 HumanProofで登録完了
- 1:30–1:55 AI Policy Studioの3ケースとOrcaRouter実行証拠
- 1:55–2:15 Issuer失効とサービス再確認
- 2:15–3:00 技術境界、価値、締め

4分ピッチでもPolicy Studioの内部項目を読み上げない。画面に残し、説明は「本人情報をAIへ送らず、曖昧な要求は自動採用しない」の一文に絞る。

### 既存実装の再利用境界

| 資産 | 扱い | 追加作業 |
|---|---|---|
| `/analyze` | 維持 | 利用者画面から外しPolicy Studioへ接続 |
| proof/issue | 維持 | 保存済みPolicyから呼ぶ |
| verify | 維持 | サービス登録完了へ結果を接続 |
| revoke | 維持 | 操作主体をDemo Issuerと表示し再検証へ接続 |
| Orca監査情報 | 維持 | provider/model/latency/request IDを裏側へ表示 |
| 現要件入力UI | 再配置 | 削除せず開発者向け補足へ降格 |

時間切れ時は、APIの作り直し・Claim Catalog拡張・本番eKYCを行わない。主体験の役割分離と成果への復帰を最優先にする。

## 実装済・模擬・構想の境界

### このPoCで実装済として示す

- サービス要件のAI分析
- OrcaRouter経由の呼び出しと監査情報
- 許可済みClaimへの構造化
- 明示同意
- 署名付き証明の発行
- 検証、期限、失効、再検証

### 模擬と明示する

- Demo Trusted Issuer
- 18歳以上 / 実在人物の元確認
- NIGHT SCREENという利用サービス
- ユーザーアカウントと本番決済

### 構想・未実装と明示する

- 実eKYC / JPKI / 運転免許証OCR / 顔認証 / ライブネス
- 複数Trusted Issuerの本番運用
- Verified Avatar / Creator / Organization / Worker
- AI Agent Trustと権限委任
- DID / VC完全準拠

## 非交渉の表現ルール

- 「過剰取得と管理リスクをゼロにする」と断定しない
- 「個人情報を共有しない」と一般化しない。共有しない具体項目を書く
- 「AIだから可能」と断定しない。AIを使う範囲とルールで足りる範囲を分ける
- `Demo Trusted Issuer` を本物のeKYCとして見せない
- 失効主体を曖昧にしない。利用者の依頼を受け、Issuerが失効する
- 未来像には各要素の近くへ `構想・未実装` と書く
- 世界初、競合不在、完全匿名、GDPR準拠などを根拠なく主張しない

## 完成条件

1. 初見の人が30秒以内に「身分証をサービスへ渡さず、必要な条件だけ証明して登録するもの」と説明できる
2. 90秒以内に登録完了まで到達できる
3. 一度もサービス要件を入力させられない
4. `AIへ送信0` と `サービスへ非共有5項目` が混同されない
5. `なぜ2つで足りる？` からAI分析とOrcaRouter実行証拠へ到達できる
6. 同意撤回とIssuer失効を別物として表示し、Issuer失効後にサービス側が再確認待ちになる
7. すべての画面で実装済 / 模擬 / 構想が判別できる
8. 3分デモ、4分ピッチ、README、記事が同じ順序・同じ数値・同じ限定表現を使う
