# 「18歳以上」を知りたいだけなのに、なぜ身分証を渡すのか — HumanProofを作った

本人確認が必要になるたび、私たちは同じような情報を別々のサービスへ渡しています。

氏名。正確な生年月日。住所。顔写真。身分証画像。

しかし、そのサービスが本当に知りたいのは、本人情報一式ではないかもしれません。18歳以上か。実在する人か。一人一アカウントの条件を満たすか。必要なのは、特定の条件に対する答えだけという場面があります。

AI HACK 2026で、本人情報の要求を必要最小限の証明へ変えるPoC `HumanProof` を作りました。

## 最初に作ったデモは、動くけれど伝わらなかった

最初の版では、画面に次を入力するようにしていました。

- サービス名
- audience / slug
- サービスの目的と現在の運用
- 現在要求している本人情報の種類

AIが文章を読み、4つの本人情報を2つのProof Claimへ変換する。その後、同意、発行、検証、失効まで試せます。

APIの動作確認としては正しい構成でした。しかし、公開デモとしては根本的な問題がありました。

来訪者は、サービス事業者として要件を書いた直後に、一般利用者として共有へ同意し、今度はIssuerとして証明を発行し、最後はサービスとして検証することになります。

一人に何役もさせていました。

「私はいま誰なのか」「VALIDになって、何ができたのか」が分かりません。説明文やバッジを足しても、役割の混線は直りません。

## 入口を、架空サービスの登録画面へ変えた

デモは、18歳以上向け動画サービス `NIGHT SCREEN` から始めることにしました。

登録の最後に、年齢確認方法を選びます。

通常の確認では身分証をアップロードする。HumanProofを選ぶと、次の画面が開きます。

共有するもの:

- 18歳以上である
- 実在する人である

サービスへ渡さないもの:

- 氏名
- 正確な生年月日
- 住所
- 顔写真
- 身分証画像

利用者が共有範囲を確認し、同意すると、Demo Trusted Issuerが期限付きの署名証明を発行します。NIGHT SCREENは署名、発行者、宛先、期限、失効状態を検証します。

大切なのは、その後です。

HumanProofで `VALID` と表示して終わらず、NIGHT SCREENへ戻り「登録が完了しました」と表示します。

利用者が欲しいのは、暗号状態の成功ではありません。サービスを使い始められることです。

## AIは、利用者の本人情報を読まない

HumanProofのAIは、本人確認書類を読んで人を判定するものではありません。

読むのは、サービス側の目的と現在の運用です。

```text
We operate an 18+ streaming service and need to confirm
each member is a real human over 18.
We currently ask for full name, exact date of birth,
home address and ID photo.
```

AIは、この要件を許可済みClaim Catalogへ写像します。

```json
{
  "required_claims": ["over_18", "human_verified"]
}
```

この呼び出しはOrcaRouterを経由します。実際のモデル、応答時間、request IDを監査情報として残します。

利用者の実名、住所、生年月日、ID番号などの値を検出した場合は、AIへ送る前にブロックします。本人確認書類の画像を送る経路はありません。

ただし、画面に表示する `AIへ送った本人情報値: 0` はヒューリスティック検査の実測です。絶対的な不存在を数学的に証明するものではありません。

## 「18歳以上」なら、AIはいらない

ここは誤魔化せません。

18歳以上なら `over_18` を要求する。この一例だけならルールで十分です。

HumanProofでAIを使う理由は、固定ルールを大げさに置き換えるためではありません。サービス導入時のPolicy設計を支援するためです。

現実の要件には、複数の目的が混ざります。

- 年齢確認には正確な生年月日や身分証原本を渡さなくてよい
- 配送には住所が必要になる
- bot対策と複数アカウント対策は別の目的かもしれない
- 「安全のため全部必要」では、何を証明すべきか決められない

AIは文章から目的を分け、許可済みClaimだけを使ったPolicy案を作ります。目的が足りなければ、勝手にClaimを確定せず質問へ戻します。

そしてPolicyは導入時に保存します。利用者が登録するたびにLLMを呼び、本人情報を送る設計にはしません。

## 同意撤回と失効を分ける

最初のデモでは、利用者が失効コードを持ち、いつでも証明を失効できるように見せていました。

これは分かりやすい一方で、概念を混ぜています。

- 共有同意の撤回: HumanProofが今後の再提示を止める
- Credentialの失効: Issuerが発行済み証明を無効化する

新しいデモでは、この2つを別の操作として表示します。

Demo Issuerが証明を失効すると、NIGHT SCREENが同じ証明を再検証して `REVOKED` を受け取り、利用状態を再確認待ちへ変えます。

## 「個人情報ゼロ」とは言わない

`over_18` や `human_verified` も、個人に関する属性です。

HumanProofは匿名化を提供するものでも、個人情報を完全になくすものでもありません。

目指しているのは、正確な生年月日や身分証原本を利用サービスごとに複製する代わりに、その場に必要な範囲の証明へ開示を絞ることです。

価値は「ゼロ」ではなく「最小化」にあります。

## このPoCで実装した範囲

実装済み:

- OrcaRouter経由のService Requirement分析
- AI送信前のPII値ブロック
- 許可済みClaim Catalogへの制約
- 明示同意
- 署名付き・短命のProof
- audienceごとのpairwise subject
- 署名、issuer、audience、expiry、revocationの検証
- 失効と再検証
- fail-closed

模擬:

- Demo Trusted Issuer
- NIGHT SCREEN
- 年齢・実在性の元確認

未実装:

- 本番eKYC / JPKI
- 複数Trusted Issuer
- Verified Avatar
- AI Agent Trust
- DID / VC完全準拠

## この先

HumanProofの出発点は、人がオンラインで自分を必要以上に晒さず、それでも必要な信頼を示せるようにすることです。

将来、人とAI Agentが同じネットワークで行動するとき、必要になる問いは増えます。

何者か。誰が許可したか。どの権限を持つか。誰のために動くか。いつまで有効か。失効できるか。

その答えを、必要最小限だけ証明する。

今回のPoCは、その一番小さな断面です。
